# ZEISS_Assessment
ZEISS  Assessment Lisbon - Backend test

## Run locally with Docker

Requirements: Git, Docker Desktop (or Docker Engine with Compose v2), and internet
access on the first run to download the .NET and SQL Server images. No local .NET SDK
or SQL Server installation is needed to run the API.

Clone the repository and start the API and database from the project root:

```sh
git clone https://github.com/alexandrepd/ZEISS_Assessment.git
cd ZEISS_Assessment
docker compose up --build
```

Compose starts SQL Server, waits until it accepts connections, applies the EF Core
migrations in a one-shot service, then starts the API. Seed products are available
after startup.

- API: http://localhost:8080/api/products
- Swagger UI: http://localhost:8080/swagger
- OpenAPI: http://localhost:8080/openapi/v1.json

To stop the API and SQL Server, press `Ctrl+C`, then run `docker compose down`.
The database is retained in a Docker volume, so it survives restarts. To reset the
database and reapply the migrations and seed data from scratch, run
`docker compose down --volumes` before starting it again.

The Compose file uses a local-development-only SQL Server password by default. To
override it, set `MSSQL_SA_PASSWORD` in the shell before starting Compose. Do not
reuse this development password in a shared or production environment.

### Run the API on the host instead

If Docker is unavailable, the API can run directly on the host. This requires the
.NET SDK version selected by `global.json` (10.0.102) and access to a SQL Server
instance. SQL Server can be installed locally on a supported Windows/Linux machine
or provided by your organization; on macOS, use an accessible remote SQL Server.

Set `ConnectionStrings__Products` to your SQL Server connection string, then apply
migrations and start the API:

```sh
export ConnectionStrings__Products='Server=YOUR_SQL_SERVER,1433;Database=ZeissProducts;User Id=YOUR_USER;Password=YOUR_PASSWORD;Encrypt=True;TrustServerCertificate=True'
dotnet tool restore
dotnet ef database update \
  --project src/ZEISS.ProductManagement.Infrastructure \
  --connection "$ConnectionStrings__Products"
dotnet run --project src/ZEISS.ProductManagement.Api --launch-profile http
```

- API: http://localhost:5257/api/products
- Swagger UI (Development only): http://localhost:5257/swagger
- OpenAPI (Development only): http://localhost:5257/openapi/v1.json

Keep credentials local; do not commit a real connection string. The API does not
create the database or apply migrations automatically.

Unit tests can run without Docker. Integration tests use Testcontainers to create
disposable SQL Server instances, so they require Docker even when the API itself is
running directly on the host.

OpenAPI is generated by ASP.NET Core. Swagger UI is provided by the NSwag.AspNetCore
package, with assets served locally; no custom HTML page or CDN is required.

## Current implementation status

`GET /api/products` reads SQL Server and returns `200 OK` with products ordered by ID,
including available stock. An empty table returns `[]`. Database failures are
reported as errors, never as an empty successful result.

`GET /api/products/{id}` returns `200 OK` with the product and available stock,
or `404 Not Found` with ProblemDetails when the integer ID does not match a product.
Both reads use the same DTO projection and preserve UTC timestamps.

`POST /api/products` persists a product and returns `201 Created` with its generated
six-digit ID, initial stock and a Location header pointing to the detail route.
The ID is assigned by the shared SQL Server sequence, not by the request body.
Invalid request DTOs return `400` before insertion. Database errors, including
sequence exhaustion, currently return a safe `500` ProblemDetails response; the
sequence never cycles back to reuse IDs.

`PUT /api/products/{id}` updates name, description and price, returning `200 OK`
with the current product, or `404` ProblemDetails if it does not exist. Description
can be cleared by omitting it or sending null. Stock is not part of the update DTO;
extra JSON fields such as stock are ignored by the default serializer. EF tracks
only changed metadata fields, so a stock change made after loading the entity is
not overwritten. UpdatedAtUtc is set; CreatedAtUtc is preserved. Concurrent metadata
updates use last-write-wins; this is not optimistic concurrency protection for metadata.

`DELETE /api/products/{id}` permanently deletes a matching product and returns
`204 No Content` with no response body. A missing product, including a repeated
delete, returns `404` ProblemDetails. The delete is a single SQL statement filtered
by primary key; it does not load the product first or reset the ID sequence.

`POST /api/products/{id}/decrement-stock/{quantity}` atomically withdraws a positive
quantity when enough stock is available. `POST /api/products/{id}/add-to-stock/{quantity}`
atomically adds a positive quantity without exceeding `int.MaxValue`. Both return
`200 OK` with the updated product and stock, `400` ProblemDetails for a non-positive
quantity, `404` for an unknown product and `409` when the operation conflicts with
the current stock level or integer range.

`GET /api/products/search?name={name}` searches for a partial product name without
case sensitivity. The `name` query parameter is required and must not be blank.
`GET /api/products/stock-level?min={min}&max={max}` returns products whose stock is
within the inclusive range. Both limits are required, must be non-negative, and
`max` must be greater than or equal to `min`. Both endpoints return `200 OK` with
product responses including stock; no matches return `[]`. Invalid query parameters
return `400` ValidationProblemDetails.

All routes are implemented in `ProductsController`; `[ApiController]` automatically
rejects invalid creation/update DTOs with `400 Bad Request` and ValidationProblemDetails.
Malformed JSON or incorrectly typed parameters can also be rejected before reaching
an action.

Search by name and stock range are filtered in the SQL query before products are
materialized, and results are ordered by ID.

Creation accepts initial stock. Updates contain only name, description and price;
subsequent stock changes belong to the dedicated stock endpoints.

## Build and tests

The unit and integration test projects require the .NET 10 SDK. Integration tests
also require Docker; they start disposable SQL Server containers through Testcontainers.

```sh
dotnet restore
dotnet build ZEISS.ProductManagement.slnx --configuration Release
dotnet test tests/ZEISS.ProductManagement.UnitTests --configuration Release
dotnet test tests/ZEISS.ProductManagement.IntegrationTests --configuration Release
```

HTTP integration tests exercise routing, DTO validation and API documentation
using WebApplicationFactory. The tests start disposable SQL Server 2022 Developer
containers with Testcontainers, apply migrations, and dispose the containers after
the tests. On Apple Silicon, SQL Server runs as `linux/amd64` and requires Docker
AMD64 emulation.

The SQL Server EF Core model is defined in Infrastructure, including product
column limits, check constraints and the bounded ProductIds sequence starting
at 100005. The initial migration reserves IDs 100000-100004 for five seed products.
Seed timestamps are fixed to keep migration generation deterministic.
The context and product query implementation are registered per request in the API.
ProductModelTests checks generated SQL without connecting to a database.

The SQL Server test image is pinned by digest. This has been verified locally but is
not an officially supported SQL Server ARM64 deployment. Docker may need internet
access on the first test run to pull SQL Server and Testcontainers helper images.
Integration tests run sequentially because each test manages a SQL Server container.

## EF Core migrations

Run from the repository root:

```sh
dotnet tool restore
dotnet ef migrations list --project src/ZEISS.ProductManagement.Infrastructure --no-connect
dotnet ef migrations script --project src/ZEISS.ProductManagement.Infrastructure
```

The design-time factory selects SQL Server without embedding a connection string.
Generating migrations and SQL does not need a running database. For applying
migrations manually, pass your local SQL Server connection string using the EF
CLI `database update --connection` option; do not commit credentials.

## Configure the product database manually

Use a running SQL Server instance and set the connection string in your local
shell (replace the example values; do not commit your actual credentials):

```sh
export ConnectionStrings__Products='Server=localhost,1433;Database=ZeissProducts;User Id=sa;Password=YOUR_PASSWORD;Encrypt=True;TrustServerCertificate=True'
dotnet tool restore
dotnet ef database update --project src/ZEISS.ProductManagement.Infrastructure --connection "$ConnectionStrings__Products"
dotnet run --project src/ZEISS.ProductManagement.Api --launch-profile http
```

Then call `GET /api/products` in Swagger. The API does not automatically create
the database or apply migrations on startup. `TrustServerCertificate=True` is
for local development only; use a trusted server certificate for deployment.
Without database configuration the documentation and routes remain accessible,
but database-backed requests return a safe `500` ProblemDetails response.

ListProductsTests verifies the HTTP list response against a separate disposable
SQL Server database, including seed stock values and an empty table.

CreateProductTests verifies creation, the Location resource, rejected input without
insertion and unique IDs from concurrent requests across two API hosts sharing SQL Server.
