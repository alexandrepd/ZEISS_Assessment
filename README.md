# ZEISS_Assessment
ZEISS  Assessment Lisbon - Backend test

## Run locally

Requires the .NET 10 SDK selected by `global.json`.

```sh
dotnet restore
dotnet run --project src/ZEISS.ProductManagement.Api --launch-profile http
```

- API: http://localhost:5257/api/products
- Swagger UI (Development only): http://localhost:5257/swagger
- OpenAPI (Development only): http://localhost:5257/openapi/v1.json

OpenAPI is generated by ASP.NET Core. Swagger UI is provided by the NSwag.AspNetCore
package, with assets served locally; no custom HTML page or CDN is required.

## Current implementation status

`GET /api/products` reads SQL Server and returns `200 OK` with products ordered by ID,
including available stock. An empty table returns `[]`. Database failures are
reported as errors, never as an empty successful result.

`GET /api/products/{id}` returns `200 OK` with the product and available stock,
or `404 Not Found` with ProblemDetails when the integer ID does not match a product.
Both reads use the same DTO projection and preserve UTC timestamps.

`POST /api/products` persists a product and returns `201 Created` with its generated
six-digit ID, initial stock and a Location header pointing to the detail route.
The ID is assigned by the shared SQL Server sequence, not by the request body.
Invalid request DTOs return `400` before insertion. Database errors, including
sequence exhaustion, currently return a safe `500` ProblemDetails response; the
sequence never cycles back to reuse IDs.

`PUT /api/products/{id}` updates name, description and price, returning `200 OK`
with the current product, or `404` ProblemDetails if it does not exist. Description
can be cleared by omitting it or sending null. Stock is not part of the update DTO;
extra JSON fields such as stock are ignored by the default serializer. EF tracks
only changed metadata fields, so a stock change made after loading the entity is
not overwritten. UpdatedAtUtc is set; CreatedAtUtc is preserved. Concurrent metadata
updates use last-write-wins; this is not optimistic concurrency protection for metadata.

`DELETE /api/products/{id}` permanently deletes a matching product and returns
`204 No Content` with no response body. A missing product, including a repeated
delete, returns `404` ProblemDetails. The delete is a single SQL statement filtered
by primary key; it does not load the product first or reset the ID sequence.

The other four routes are declared but not implemented. Requests with valid
HTTP binding and valid request DTOs return `501 Not Implemented` with ProblemDetails.
Routes are grouped in
`ProductsController`; `[ApiController]` automatically rejects invalid creation/update
DTOs with `400 Bad Request` and ValidationProblemDetails. Malformed JSON or
incorrectly typed parameters can also be rejected before reaching an action.

For the four reserved routes, OpenAPI lists intended success response schemas
as the future contract, not as currently available behavior. Stock-operation and search/filter validation,
business operations and the remaining HTTP error contracts will be connected
when the use cases are implemented.

Creation accepts initial stock. Updates contain only name, description and price;
subsequent stock changes belong to the dedicated stock endpoints.

## Build and tests

```sh
dotnet build --configuration Release
dotnet test tests/ZEISS.ProductManagement.UnitTests --configuration Release
dotnet test tests/ZEISS.ProductManagement.IntegrationTests --configuration Release
```

HTTP integration tests exercise routing, DTO validation and API documentation
using WebApplicationFactory. ProductPersistenceTests requires a running Docker
engine and starts a disposable SQL Server 2022 Developer container using
Testcontainers. It applies migrations twice, checks the five seed IDs and saves
and reloads a product with ID 100005. Containers are disposed after the test.

The SQL Server EF Core model is defined in Infrastructure, including product
column limits, check constraints and the bounded ProductIds sequence starting
at 100005. The initial migration reserves IDs 100000-100004 for five seed products.
Seed timestamps are fixed to keep migration generation deterministic.
The context and product query implementation are registered per request in the API.
ProductModelTests checks generated SQL without connecting to a database.

The SQL Server test image is pinned by digest. It runs as linux/amd64; on Apple
Silicon it requires Docker AMD64 emulation. This was verified locally but is not
an officially supported SQL Server ARM64 deployment. Docker may need internet
access on the first test run to pull SQL Server and Testcontainers helper images.

## EF Core migrations

Run from the repository root:

```sh
dotnet tool restore
dotnet ef migrations list --project src/ZEISS.ProductManagement.Infrastructure --no-connect
dotnet ef migrations script --project src/ZEISS.ProductManagement.Infrastructure
```

The design-time factory selects SQL Server without embedding a connection string.
Generating migrations and SQL does not need a running database. For applying
migrations manually, pass your local SQL Server connection string using the EF
CLI `database update --connection` option; do not commit credentials.

## Configure the product database

Use a running SQL Server instance and set the connection string in your local
shell (replace the example values; do not commit your actual credentials):

```sh
export ConnectionStrings__Products='Server=localhost,1433;Database=ZeissProducts;User Id=sa;Password=YOUR_LOCAL_PASSWORD;Encrypt=True;TrustServerCertificate=True'
dotnet tool restore
dotnet ef database update --project src/ZEISS.ProductManagement.Infrastructure --connection "$ConnectionStrings__Products"
dotnet run --project src/ZEISS.ProductManagement.Api --launch-profile http
```

Then call `GET /api/products` in Swagger. The API does not automatically create
the database or apply migrations on startup. `TrustServerCertificate=True` is
for local development only; use a trusted server certificate for deployment.
Without database configuration the documentation and reserved routes remain
accessible, but listing products returns a safe `500` ProblemDetails response.

ListProductsTests verifies the HTTP list response against a separate disposable
SQL Server database, including seed stock values and an empty table.

CreateProductTests verifies creation, the Location resource, rejected input without
insertion and unique IDs from concurrent requests across two API hosts sharing SQL Server.
